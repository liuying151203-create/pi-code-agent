# 开发问题记录

这里只记录开发中实际出现并已定位的问题。每条包含现象、原因、修复和验证方式，方便后续章节避免重复踩坑。

## B001：普通问候触发大量工具调用

- 现象：输入“你好”后，Agent 扫描工作区、读取文档并执行多条 shell 命令。
- 原因：早期系统提示词只要求“使用工具解决任务”，没有明确简单对话的工具边界和停止条件。
- 修复：使用简短中文提示词，明确问候直接回答、仅在任务需要时调用工具，并要求使用最少行动。
- 验证：输入普通问候时不应产生工具调用。

## B002：模型请求看起来像卡住

- 现象：发送消息后终端长时间没有新输出，不清楚程序仍在等待还是已经失败。
- 原因：模型请求缺少可见的等待状态、超时限制和统一错误反馈。
- 修复：增加请求中提示、可配置超时和异常信息；关联提交 `01941c4`。
- 验证：请求时显示超时秒数，超时或连接错误后返回交互循环。

## B003：直接运行章节文件时导入失败

- 现象：运行 `python s05_session_persistence/code.py` 时出现 `ModuleNotFoundError`。
- 原因：直接运行文件时，Python 主要把章节目录放入模块搜索路径，无法稳定找到项目根目录下的其他章节包。
- 修复：统一从项目根目录使用模块方式运行，例如 `python -m s05_session_persistence.code`；关联提交 `f3603ef`。
- 验证：README 中的所有章节启动命令都使用 `python -m`。

## B004：不同章节误用同一份会话记录

- 现象：s05 和 s06 共用 `.sessions` 后，较新章节可能读到结构不同的旧 JSONL 记录。
- 原因：章节逐步演进了持久化格式，但默认会话目录没有随格式隔离。
- 修复：按章节使用 `.sessions/s05`、`.sessions/s06` 等独立目录，不增加无价值的跨章节兼容代码；关联提交 `70fd4f4`。
- 验证：各章节默认新建的会话文件只出现在自己的目录中。

## B005：摘要模型没有返回最终文本

- 现象：上下文压缩请求结束后只有思考内容，没有可写入会话的摘要文本。
- 原因：较小的输出额度可能被推理过程耗尽；不同模型返回内容块的方式也不完全一致。
- 早期处理：不足 1024 token 时重试至 1024；仍失败则生成确定性回退摘要。这只能保住任务要求，不能保证代码证据仍在模型上下文中，B008 证明继续运行仍可能反复重读。
- 当前修复：s07 的 Anthropic 摘要请求显式关闭思考，空摘要停止压缩而不覆盖原始上下文；s10 选择接口专用选项，s11 保存失败诊断及用量。是否能关闭思考仍取决于服务支持，见 B009。
- 验证：摘要参数仅用于摘要；空摘要时原始会话保持不变，没有回退压缩记录；失败请求已消耗的用量仍保留。

## B006：上下文压缩不收敛并产生滚动失真

- 现象：压缩后上下文仍超过阈值，下一次请求立即再次压缩；旧摘要还会被反复总结而逐渐缩水或失真。
- 原因：旧实现按消息条数保留尾部，少量巨型工具结果也可能超过预算；同时把旧摘要当作普通消息再次总结。
- 修复：改为按字符预算保留尾部，单个工具结果进入摘要请求前先截断；旧摘要与新增消息分开传递，并在落盘前复核压缩后大小；关联提交 `d955ea6`。
- 验证：包含超大工具结果的测试中，压缩后的上下文必须低于阈值；连续压缩时旧摘要不出现在新增消息列表中。

## B007：只读分析反复申请 shell 权限

- 现象：分析一个位于大文件中部的方法时，Agent 先读取整份文件；压缩后目标代码丢失，随后反复尝试 PowerShell、`findstr` 或 Python 命令并触发权限确认。
- 原因：`read_file` 原先不能按行范围读取；摘要输入又只保留巨型工具结果的开头，导致模型只能换用 shell 重新定位代码。
- 修复：为 `read_file` 增加 `start_line` 和 `limit`；工具定义负责解释参数，系统提示词只要求“大文件分段读取”和“拒绝后不换等价命令重试”；关联提交 `78cbcef`。
- 验证边界：参数与提示词只能支持分段读取，不能保证模型实际使用，也不能保证拒绝后一定停止。s12 再次出现同类问题，见 B008；必须同时验证工具输出预算与运行时停止条件。

## B008：s12 读取技能与代码后反复搜索

- 归属：这是工具结果过大、s07 空摘要回退与运行时缺少停止边界的组合问题，s12 是复现场景，不是所有机制的引入章节。
- 复现：新建 s12 对话，输入“按 code-review 技能，只读审查 s12_skill_loading/code.py 中的 SkillCatalog.scan，指出有证据的问题”。本地证据来自 `trace-20261003-041431-425958.jsonl` 与对应会话；运行数据不提交 Git。
- 证据：技能和代码均读取成功，分别返回 304 和 12,761 字符。模型随后产生约 1.7 万字符思考；第一次压缩从 35,856 字符降到 228 字符，保留消息数为 0。共发生 7 次空摘要回退，摘要响应均达到 1024 token 输出上限。一次 `findstr /s /n /i "def read_file" *.py` 还扫入 `.venv`，返回 4,431,262 字符。
- 原因：B007 只增加可选读取窗口，缺少强制返回预算；模型选择全量读取及递归搜索后，最新工具交互超过保留预算。空摘要回退只保留用户要求与历史路径，不保留代码和技能正文；循环没有请求轮数上限，于是再次读取与搜索。这里是信息丢失后的重复运行，不是技能扫描失败；不能靠调大阈值认定已修复。
- 早期修复与归位：读文件窗口、存档和技能范围约束曾放在 s12；空摘要策略归入 s07，诊断与 12 轮保护归入 s11。B010 证明只限输出与轮数仍不能完成任务；当前工具预算归入 s02/s03，s07 改用模型窗口预算，s11 的限轮改为可选，s12 直接复用。
- 回归：`tests/test_s12_skill_loading.py` 验证默认/显式大读取、字符边界、分段重组、越界路径、超长结果存档、空摘要不落盘且不请求回答模型、持续工具调用按轮数停止。模型遵守技能说明的程度仍需真实模型复测，离线测试不宣称任务必定完成。
- 经验：区分“工具有这个参数”“模型用了这个参数”和“运行时强制保证边界”；摘要回退“不崩溃”不等于保留了完成任务所需的证据。同类复发必须关联旧条目，并补充旧修复未覆盖的边界。

## B009：摘要额度提高后仍无正文，缺少响应结构证据

- 归属：s07 的摘要请求策略、s10 的接口参数适配、s11 的诊断观察；s12 仅复现并复用。不能因发生在 Skills 任务中就把修复归入 Skills 章节。
- 关联：B005 的空摘要在 B008 防失控修复后仍会发生；“失败后停止”没有解决摘要生成失败本身。
- 证据：`trace-20261003-062402-060013.jsonl` 的摘要请求输入 3527、输出 4096 tokens，约 18.4 秒后返回 `max_tokens`，随后发出 `summary_empty`。这次运行共 6 次模型请求、9 次工具调用；会话保留 11 条消息和 1 条失败记录，没有回退压缩。
- 初次判断：输出额度被用尽且提取正文为空可以确认；旧 Trace 未保存内容块结构，当时无法排除响应转换或解析丢失内容。1024 提高到 4096 仍失败，不能把预算偏小认定为唯一根因。
- 新诊断证据：`trace-20261003-064811-825172.jsonl` 中摘要输入 4209、输出 4096 tokens，约 20.5 秒后返回 `max_tokens`；`content_types=["thinking"]`、`thinking_chars=8754`、`text_chars=0`、`extracted_text_chars=0`、`other_blocks=[]`。本次接收到的响应只有思考，没有可用正文，不是正文提取漏掉了已有 text 块。诊断仍位于 Provider 转换之后，不能据此判断兼容服务内部路由、默认思考设置或其关闭参数是否生效。
- 当前修复：s07 默认给 Anthropic 摘要请求发送 `thinking: {"type": "disabled"}`；s10 用 `summary_request_options(provider)` 选择参数，Chat Completions 不携带 Anthropic 专有字段。s11 记录空摘要的结构、长度、额度、用量与实际请求的 `requested_thinking`；终端观察者与 Trace 复用同一事件，不重复计费。空摘要停止且不写回退压缩；正常任务不关闭思考，配置与会话格式不变。
- 验证：s07 测试检查默认选项、覆盖选项及失败不落盘；s10 测试检查参数依据接口而非模型名；s11 测试用条件响应验证关闭参数确实到达 SDK、摘要可落盘且正常请求不携带它，同时覆盖诊断脱敏与用量只计一次。s12 测试验证直接复用运行时组件，诊断单元测试已移到 s11。
- 验证边界：真实复测已确认旧请求“只有思考且耗尽额度”；新请求的兼容服务支持情况尚未经过付费 API 验证。若诊断显示 `requested_thinking=disabled` 仍返回只有思考，说明服务未按预期返回正文，应确认服务能力或选择摘要模型，不能宣称离线测试证明了服务兼容。

## B010：摘要成功后仍反复定位代码并耗尽固定轮数

- 关联与归属：B007/B008 的搜索、证据保留和运行保护问题；不是 B009 的空摘要，也不是 Skills 扫描失败。工具属于 s02，权限属于 s03，压缩预算属于 s07，已知 usage 与可选轮数属于 s11；s08-s10/s12 的入口同步复用。
- 复现证据：`trace-20261003-095207-523182.jsonl` 与对应会话。原只读审查任务执行 12 次回答请求、2 次摘要、13 次工具调用，已知 Token 72,220；两次摘要均 `end_turn`，压缩为 31,424→14,333 与 25,654→14,897 字符。固定轮数耗尽时没有审查结论。
- 具体问题：工具首读 170 行附近返回 2579 字符，进入摘要区时前 2000 字符恰好停在 `for m…`，一部分目标实现没有交给摘要模型；压缩后又读取 205、258、170 行附近。模型还使用 `findstr -A 40`，这是不支持的选项；shell 中文结果有乱码，旧执行函数又没有根据退出码报告失败。
- 原因边界：Pi 同样会对摘要区单条工具结果取前 2000 字符，不能把该机制本身认定为错误。差异是本项目固定 24,000 字符触发压缩、近期仅 12,000 字符、s12 专用 80 行/4000 字符窗口，加上 12 轮硬停止；它们使同一个短审查过早压缩并消耗补读轮数。重复读取也可能是验证需要，源码与日志不能证明模型每次读取的动机或唯一根因。
- 修复：s02 引入独立 2000 行 / 50 KiB UTF-8 预算，read_file 保留完整行并给继续位置，bash 保留末尾并存档、报告非零退出；新增指定文件的字面 grep。s03 只为 grep 增加工作区校验和只读权限，不放宽复合 shell。s07 改为实际模型窗口减预留 Token，近期默认保留 20,000 Token；内部仍近似分割，不删除 Pi 的 2000 字符摘要策略。s11 用最近有效正常回答 usage 加后续消息估算校准，不用会话累计消费；限轮通过 `AGENT_MAX_ROUNDS` 可选开启，默认关闭，不增加强制收尾。s12 删除专属工具预算，保留完整核心循环并直接复用。
- 配置迁移：实际模型窗口必须填写 `MODEL_CONTEXT_WINDOW_TOKENS`，旧字符阈值不再读取；`SESSION_COMPACTION_SUMMARY_MAX_TOKENS` 已填写的值仍会覆盖默认额度。没有改写用户 `.env`，也没有宣称知道兼容服务实际窗口。
- 回归：s02 测试 UTF-8 字节预算、继续位置、超大单行、搜索行号/匹配上限、shell 全文与末尾；s03 测试搜索只读和越界拒绝。s07 测试短审查超过旧 24,000 字符但不提前压缩，以及传入实际估算可触发。s11 测试当前上下文与累计用量分离、压缩后不重用旧 usage，以及 s11/s12 默认能在第 14 次请求正常结束、显式上限仍生效。
- 验证边界：离线条件响应与合成记录验证运行时机制，未调用付费 API，不能等同于原真实审查完成率。默认取消硬上限存在持续消费风险；可明确设定正整数保护，模型仍可能选 shell 或反复验证。终端前 200 字符预览只影响展示，不是模型收到的工具正文长度。

## B011：只读任务缺少运行模式，空工具列表意外回退

- 关联与证据：用户测试只读任务时反复批准 bash，关联 B007/B010；旧代码始终提供混合工具集，读文件参数和技能说明不能禁止模型选择 shell。另一个可直接定位的问题是 s03 的 `tools=tools or TOOLS`，显式空列表会重新发送全部默认工具。
- 原因与边界：任务措辞“只读”并不是运行时授权。复合 shell 触发确认符合旧规则，不能把所有确认都当成误报，也不能把提示词或取消确认视为沙箱。
- 修复：只读机制在 s03 增加 `--mode read-only`，模型只看到 glob、grep、read_file；实际执行继续通过同一个 execute_tool，注入只读权限函数，拒绝 shell、写入、编辑、未知工具和常见敏感路径，不请求批准。工具默认值改为仅在 None 时使用 TOOLS。普通模式规则保留，没有审批缓存或自动提权。
- s04 接入：入口选择 s03 的工具与权限函数，将后者传给已有 make_permission_hook，再注册进 Hooks；循环不新增模式分支，只同步 None/空列表的工具默认值行为。
- s05–s12 接入：s05 将启动选择拆为 `parse_session_args()` 与 `select_session_path()`，删除旧解析包装，避免命令行重组和二次解析；s06–s12 入口共用这两个方法，传入本章会话目录。各章 main 显式选择 active_tools 与 permission_hook，继续复用 s03/s04 的工具和 Hook。存储格式、保存顺序和各章核心机制不变，历史不恢复授权；空工具列表仅在 None 时回退。
- 回归：`tests/test_s03_permission.py` 验证工具集合、越界及敏感路径、拒绝时不确认也不分发、模型仍返回禁止调用时文件不变，以及 glob/grep/read_file 正常执行。离线 main 测试覆盖默认模式与只读模式的真实参数组装；空列表不恢复全部工具；无效模式在初始化模型前失败。
- s04 回归：`tests/test_s04_hooks.py` 验证非只读调用在前置阶段阻断且不请求批准、不执行后续前置 Hook，但后置 Hook 仍接收拒绝结果；三种只读工具正常走完整生命周期，阻断结果回传模型，main 实际筛选工具并注入相应权限函数。默认模式继续确认写入；无效模式不初始化模型。
- s05 回归：`tests/test_s05_session_persistence.py` 用离线 main 验证新建及加载历史时只读策略仍生效，旧工具不重放、禁止调用不执行且不批准；用户、assistant、拒绝及正常工具结果均按原顺序保存。普通模式继续批准写入，空列表不恢复工具，无效模式不创建会话；共用解析方法只返回选项、不写文件，路径选择保持新建和恢复规则。
- s06–s12 回归：`tests/test_read_only_runtime.py` 逐章运行真实 main，仅替换 SDK/Provider 出口；验证新建与恢复、bash/写入/编辑/敏感或越界读取/未知工具拒绝，三种只读工具实际执行、结果与回答保存，普通模式仍批准写入，空列表不回退；--help 和无效参数均在配置及客户端初始化前退出。
- 验证边界：不调用付费 API，不证明模型一定收敛。只读是工具入口的限制，不是 OS 隔离或任意秘密扫描；直接调用底层 handler 的宿主程序不在此授权边界内。

## B012：开发任务反复审批，缺少可以放权的隔离执行边界

- 关联与证据：用户在 B007/B010/B011 修复后仍反馈开发测试需要反复批准 bash。s03–s12 的普通模式直接在宿主执行命令；只读模式虽然不审批，却不能写代码或运行测试，不能解决开发任务的放权需求。
- 原因与边界：提示词、工作目录和危险命令正则都不是 OS 隔离。直接去掉确认会放开宿主 shell；不能将“减少重复审批”修成“宿主无保护自动执行”。重复搜索或模型不收敛仍是另外的问题。
- 实现：新增独立 s13，将全部六种工具交给无宿主挂载、无网络、非 root、只读根文件系统和资源限制的 Docker 容器；副本内自动执行，退出只导出审查 Diff。宿主模型密钥和会话不传入容器，隔离失败停止并补齐工具消息，不回退宿主。s03–s12 的源码和权限行为不变。
- 回归：当前对应 `tests/test_s13_a_sandbox_copy.py`，离线检查固定 Docker 参数、stdin 协议、真实 tar 解压、凭证过滤、宿主原文件不变、Diff、致命失败停止和批次配对，以及导出/清理失败必须报错；显式开启的 Docker 集成测试检查实际隔离。
- 验证边界：本次 Docker Desktop Linux 引擎未运行，未启动服务、下载镜像或调用付费模型；离线验证不等于真实容器隔离验证。容器不是绝对安全，秘密过滤不是通用脱敏，沙箱不保证模型完成任务或控制模型费用。

## B013：隔离副本完成任务，却没有对话内交付修改的入口

- 关联与复现：B012 引入的原 s13 只在退出时导出 Diff。用户实际运行“新建 sandbox_demo.py 并断言 add(2, 3) == 5”，会话记录和工具结果确认输出 `ok: 5`、`exit=0`；退出后 Diff 完整保存新增文件，但原仓库没有该文件，也没有无需退出即可预览/交付的入口。
- 原因：隔离执行成功不等于修改交付完成。原实现把报告导出放在 finally，缺少宿主确认应用和应用后比较基线的职责；这不是模型没改文件，也不是 Docker 丢失修改。
- 修复：将原 s13 整理为 s13-A（`s13_a_sandbox_copy`），新增 `WorkspaceSync.preview/apply`。每轮任务后保存预览；宿主 `/diff`、`/apply` 不进入模型消息，确认后应用固定版本。复核路径、容器版本和宿主前像；冲突整批拒绝，成功才推进基线，退出只保存未应用修改。回写尝试保存补丁和原内容备份，不自动提交。
- 边界：只交付普通非空 UTF-8 文本；不回传链接或权限，二进制/空文件等变化阻止整批应用。写入阶段失败禁用后续回写，不承诺并发编辑或磁盘故障下的事务回滚；宿主外部编辑不自动反向同步到容器。
- 回归：`tests/test_s13_a_workspace_sync.py` 使用真实 Git 在临时目录验证两轮新增/修改/删除、换行、冲突、版本变化、路径边界、失败备份和基线；`tests/test_s13_a_sandbox_copy.py` 运行真实 main 验证默认取消、明确确认、不退出即可两轮交付、命令不计模型请求，以及真实 Docker 的两轮交付测试。
- 验证边界：离线测试不启动容器、不调用付费模型；本次 Docker Linux 服务未运行，未自行启动或重建镜像，A 版本真实容器回归须在用户准备镜像后显式执行。旧 s13 运行记录保留，未删除或自动迁移。

## B014：修改已应用，退出提示仍像有未交付内容

- 复现：用户 `/apply` 输入 `y`，看到“已应用 1 个文件”，随即 `q` 退出，却仍看到“未应用 Diff 已保存”，容易误认为交付未成功；关联 B013。
- 原因：退出预览后无条件输出保存提示，没有区分空 Diff 与剩余修改；回写和基线更新本身正常。
- 修复边界：s13-A 依据 `changed_files` 区分无剩余修改和未应用 Diff；仅在容器清理成功后提示清理完成。只调整提示，不改变补丁、确认、备份和清理行为。
- 回归：`tests/test_s13_a_sandbox_copy.py` 验证两轮成功应用后的退出提示、取消应用后保存未应用 Diff，以及导出/清理失败不伪报成功；使用离线 Docker 替身和真实临时 Git 操作，不启动 Docker 或请求模型。

## B015：Windows 原生 Worker 启动命令的引号需要匹配内层 cmd

- 证据：开发 s13-C 时，用本机 `cmd /d /s /c` 验证包含空格参数的固定 Python 命令。把内层命令作为 Python 列表参数再转换，返回 `Access is denied`；按内层 cmd 的原始命令行传入、保留额外外层引号后，同一安全诊断输出 `A B`。这不是用户运行日志，也没有启动原生 runtime。
- 原因边界：外层 Node argv 与内层 cmd 命令字符串不是同一层解析。`cmd /s /c` 剥掉最外层引号，重复使用通用 argv 转义会改变内层字节；不能仅根据 `Access is denied` 就认定是 ACL 或 sandbox-runtime 的缺陷。
- 修复：s13-C 的固定 Worker 命令加外层引号，与上游 Windows 内层 raw passthrough 对应；模型工具参数始终走 stdin JSON，不参与宿主 shell 字符串，不增加本地回退。
- 回归：`test_fixed_windows_worker_command_handles_spaces_without_running_runtime` 使用真实 Windows cmd 和可信 Worker，只在临时项目写入测试文件；它验证引号和工具接线，不证明原生 OS 隔离，后者仍需显式 C 集成测试。
