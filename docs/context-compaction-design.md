# 上下文压缩设计

## 先明确要解决什么

完整会话记录越来越长时，不能一直把全部记录发给模型。压缩要保留完整记录供恢复和查看，同时让后续请求使用“历史摘要 + 最近消息”。这是会话运行时的核心能力；扩展可以调整压缩，默认流程不能依赖扩展存在。

2026-10-28 复核：当前正式包及 s06 还没有压缩、窗口信息或会话总用量统计。现有 `Usage` 只有输入/输出，CLI 只统计一次输入；`AgentSession._history` 同时承担完整历史与请求上下文。`SessionStore` version=1 只认消息和 custom 状态条目，严格检查字段。简单截断 `_history` 或只加摘要函数会丢失恢复依据，也可能破坏工具调用与结果的关联。

## 数据和执行流程

### 1. 会话记录与请求上下文

会话记录只追加，包含原消息、custom 状态和压缩记录；不会因压缩删除原有消息。每条记录有稳定 ID，`first_kept_entry_id` 指向最近消息的首条记录。

请求上下文从当前活动记录构建：

```text
无压缩记录：        原始消息
有最新压缩记录：    摘要消息 + 首个保留条目及之后可见的消息
```

压缩后追加的新消息也进入上下文。连续压缩时，使用上次摘要及上次保留起点之后需要压缩的消息生成新摘要，只使用最新有效压缩记录构建上下文；不能丢掉之前保留下来、这次又被压缩的内容。custom 状态条目不发给模型，custom 消息保留现有模型可见性语义。摘要应作为有明确来源的内部消息，再转换为供应商支持的文本消息；不能假装是用户实际输入，也不能被当成需要重复落盘的普通会话消息。

`AgentSession` 是状态所有者：完整会话记录、当前请求上下文和工具状态要分别可读。`messages` / `prompt()` 返回值、事件中的新增消息和扩展 `context` Hook 的具体范围必须在 s07 README、SDK 和回归中明确；不得悄悄把原先的“完整历史”返回值改成摘要后的短列表。`context` Hook 在每次请求的活动上下文上执行，结果仍只影响本次请求，不改持久记录；摘要消息必须通过对应的消息校验和 `convert_to_llm`。

具体接线：`_history` 仍按既有契约保存完整消息并用于返回值/事件；每次真正请求模型前，循环通过会话提供的上下文构建入口取得“摘要 + 保留消息”。s07 的 s06 快照需要新增这个最小请求上下文入口；不传入该入口时，低层 `agent_loop` 保持原行为。正式产品已有 `transform_context`，将“构建压缩后的上下文”和“调用扩展 context Hook”按顺序组合，再交给 `convert_to_llm`；不能让 Hook 重新得到未压缩的完整历史。工具/消息完成后的记录仍先于下一次上下文构建，避免用旧记录遗漏本轮工具结果。

无磁盘模式也需要有带稳定 ID 的内存条目和压缩记录，才能复用同一构建流程。使用内部内存会话记录，保持现有 `store=None` 的公开含义；不要为了实现它提前引入多余的可插拔框架。

### 2. s07 手动压缩

```text
/compact [可选要求] 或 session.compact(instructions)
  → 占用会话并完成已有运行的取消/收口
  → 读取当前活动记录、识别上次摘要
  → 从最新记录往前估算，找到近期消息保留起点
  → 对较早内容生成摘要；必要时另总结被切开的当前回合前缀
  → 追加压缩记录并确认写入
  → 基于记录重建请求上下文 → 释放会话
```

参考 Pi：手动压缩时先中止当前运行并等待收口。正式产品复用现有 `abort()` / `wait_for_idle()`；s07 教学快照只补完成该行为必需的单任务取消与等待，不提前加入 s11 队列。压缩期间新的 prompt、重载和另一次压缩须按同一忙状态拒绝或等待，不能并发修改记录。只在工具批次安全收口后切分，不执行已有工具调用。

手动入口由外部任务等待收口，活跃工具或监听器不能等待自己空闲；这种重入调用必须明确拒绝，防止死锁。自动压缩发生在当前运行的安全边界，走内部已占用会话的路径，不能再调用会等待自己的公共手动入口。开始通知、摘要请求、记录提交或结束通知失败时，都要释放忙状态；成功写入但进程在发布内存上下文前退出时，重开须根据已写入的记录重建。

对外接口：SDK 使用 `await session.compact(instructions=None)`，成功返回包含摘要、保留起点和摘要用量的结果；无可压缩内容或失败明确报告。CLI 识别 `/compact` 和 `/compact <要求>`，由同一 `session.compact()` 执行，命令文本不自动进入对话或触发普通回合。s07 教学入口在普通输入前用简单判断分发，不提前加入命令注册机制；正式产品接入已有的 `run_command`，并处理同名扩展命令冲突。新增压缩开始/结束通知供界面观察，扩展专用 Hook 在 s09 接入，s10 命令章节再统一讲解命令分发。

切点按 Pi 的近期 token 估算选择：可从用户消息或模型消息开始，不能从孤立工具结果开始；保留工具调用时，其结果也必须保持完整顺序。单个回合过长时按 Pi 的 split turn 规则保留后半段并总结前缀；确实无可压缩内容时报告原因，不写空摘要或假成功。

摘要由当前模型执行独立请求，不带业务工具，不追加为普通用户输入；在摘要中保留目标、约束、进度、决定和必要上下文。正常有效文本才允许提交。错误、取消、空结果或额度截断均不发布新的压缩记录，也不替换正在使用的上下文；显示实际失败。摘要请求的真实 usage（若有）写入压缩记录，不计成普通对话消息或假定为零。当前没有读写文件工具时不伪造 Pi 的文件操作清单；随实际工具在对应章节补充。

摘要输出额度按 Pi 的预留预算受当前模型输出上限约束；不得把上下文窗口大小直接当作输出额度。已有 `max_tokens` 的实际配置继续生效，额度不足导致摘要截断时按失败处理。

### 3. 持久化和兼容

新增项目自己的 version=2 会话格式，在现有消息/custom 条目之外增加 `compaction` 条目：`id`、`parent_id`、`timestamp`、`summary`、`first_kept_entry_id`、`tokens_before`（未知时显式为 null）以及可选 `usage`。字段命名遵循 Python；它不是 Pi 的 JSONL 格式。校验保留起点属于当前线性历史、位于压缩记录之前并能构建有效工具序列；错误记录必须明确报错。

version=1 文件必须可读取，普通续聊不强制改写。首次对 version=1 写压缩记录前，在同目录完成 version=2 转换：验证旧文件和转换结果，保留一份不可覆盖的旧版备份，再原子替换；目标/备份冲突、磁盘失败或文件外部变更则停止，不覆盖用户数据。保留原条目 ID、parent 顺序、消息、custom 数据和原始内容；不能覆盖用户文件、只改内存或静默创建另一个路径。写入压缩记录仍遵守先持久化、后发布新上下文；若写入结果不确定，锁住会话并要求重新打开检查。

旧版程序无法读取 version=2，应明确报告版本不兼容；备份可供旧版本使用，但不会包含后续新增消息。`store=None` 不创建文件，内存压缩行为与持久模式一致。会话树/跨分支恢复目前另行排期，不把线性记录实现称为 Pi 树格式兼容；未来树实现必须重新验证压缩记录属于当前分支路径。

### 4. s07 第二阶段：自动触发和用量

以 Pi 为参照，先将模型窗口、预留输出预算、近期保留预算放入明确配置；SDK 可显式构造，CLI 支持配置并显示未知/禁用原因，不根据模型名猜。统计要区分：

建议公开 `CompactionSettings(enabled=True, reserve_tokens=16384, keep_recent_tokens=20000)`，模型配置增加可选 `context_window`；CLI 对应显式配置项，具体名称在 s07 第二阶段与现有 `.env` 校验一并落地。自动触发开启但窗口未知时报告无法判断，只有提供合法窗口后才计算阈值；SDK 查询同样返回未知，不返回伪造百分比。现有调用不传新参数仍可构造和继续对话。

1. 单次回答用量；
2. 本次输入累计消耗；
3. 完整会话累计消耗（包含已压缩掉的历史和摘要请求）；
4. 当前上下文占用估计。

当前上下文不能用所有请求消耗之和代替。按 Pi 的 `estimateContextTokens`：优先用最近一条有效、压缩后适用的模型 usage 作为锚点，再估算后续消息；没有有效 usage 时使用消息估算并标明估算来源。压缩完成、还没有新的有效回答时，展示的当前占用为未知；内部估算用于阈值判断时必须区分来源，不能把压缩前旧 usage 当作新窗口占用。`error/aborted`、全部为零及过期的 usage 不当作有效锚点。

Provider 的缓存字段必须先按协议归一化：Anthropic 的未缓存输入和缓存读/写分项需要合并成上下文输入；OpenAI 的 prompt 总数已包含缓存命中，不能再重复相加。供应商不提供缓存明细时保留未知。会话累计应覆盖所有已记录的回答和摘要 usage，保留未返回用量的未知标记；不增加缺少可靠费率的伪费用。

新增 usage 字段采用可选值，旧版只含 `input_tokens`/`output_tokens` 的消息仍能读取；新的 version=2 记录要覆盖完整响应与流式尾块的同一归一化结果。`SessionStore` 的严格消息编解码和 context Hook 校验同步更新，不能只改 `Usage` 类而使旧会话无法恢复。SDK 获取会话累计统计时从完整记录计算，CLI 的 `[本次用量]` 继续只统计这次输入；摘要请求有独立来源，不能混成普通模型回答或重复累加。

自动压缩由某次用户输入触发时，它的摘要请求消耗属于这次输入，应计入该次 `[本次用量]`，同时只计入一次会话总计；用户单独执行 `/compact` 时，展示该命令的摘要请求用量，不改之前输入的统计。摘要缺失 usage 时保留“不完整/未知”，有实际记录才计数。

模型响应和压缩记录需保留可选的 provider/model 来源，用于区分不同模型的历史 usage 与溢出；旧记录来源未知时不把它冒充当前模型。模型切换后不能拿上一个模型的溢出错误或旧用量当作当前模型的直接结论；对于来源未知的旧记录，按估算或未知处理，不能直接认定为同一模型的真实 usage。

自动触发条件与 Pi 一致：`context_tokens > context_window - reserve_tokens`。检查位置：新输入请求前、完整工具批次结果入历史且确实需要下一次模型回答前、一次运行结束后的收口。不得在工具调用和工具结果之间压缩；终止工具批次且没有排队输入时，不为一个不会发生的下一请求做批次间检查。与 `input`、`context` Hook、资源展开、动态工具快照的调用顺序在实施时按 Pi 对应路径核实并写进测试，不能只在 CLI 接线。

服务明确报告上下文溢出、或符合 Pi 已验证的可恢复截断条件时，先保留失败记录，构造可继续的上下文，成功压缩后最多恢复该次模型请求一次；已完成工具不重跑，未投递消息不丢失。普通网络错误、用户取消、一般输出额度截断不能一律当上下文溢出。SDK 包装异常需要保留可分类的原始原因；无法可靠分类时明确失败，不按报错文字猜成功。摘要失败或压缩后仍溢出时停止并报告，不能循环压缩/重试。

### 5. s09 扩展介入

核心负责切点准备、默认摘要、记录和恢复；扩展事件在此之上对齐 Pi 的 `session_before_compact`、`session_compact`、`session_compact_failed`。压缩前事件包含准备结果、原因、可选用户要求及是否准备恢复请求；扩展可取消或提供自定义摘要/保留起点及可选用量。来自扩展的结果必须经过同样的类型、切点和持久化校验，不能绕过工具边界。事件失败和取消的分流、多个扩展顺序、旧代次失效与重载期间忙状态，在对应 Pi runner 源码和测试核对后明确实现。

## 验收清单

- s07：两个独立回合、带多工具的回合、单个超长回合；验证真实截取范围、摘要模型收到的内容、下一次模型实际请求与旧记录均正确。摘要失败/截断/取消不产生新记录；手动压缩忙时中止并等待；重复压缩不丢上次摘要；`store=None` 可用。
